## 2. 背景知识

### 2.1 LDM/STM：一次搬一组寄存器

`STMDB sp!, {r0-r3, lr}` 就是 C 函数序言 `push {r0-r3, lr}` 的真身——
编译器靠它保存现场，靠 `LDMIA sp!, {r0-r3, pc}` 恢复。四种寻址模式由
P（前/后）、U（增/减）两位组合：

| 模式 | 编码 | 最低地址 | 结束后基址 | 通俗名字 |
|------|------|----------|-----------|----------|
| IA | P=0 U=1 | base | base + n×4 | `STMIA`（存后增）/ `LDMFD`（出栈） |
| IB | P=1 U=1 | base+4 | base + n×4 | `STMIB` |
| DA | P=0 U=0 | base−n×4+4 | base−n×4+4 | `STMDA` |
| DB | P=1 U=0 | base−n×4 | base−n×4 | `STMDB`（**入栈**）/ `LDMED` |

实现时最容易犯的错（我们都犯过了）：

1. **"递减"只描述基址怎么算，不改变寄存器到地址的映射**——无论哪种
   模式，编号小的寄存器永远在低地址。满递减栈压入 {r0,r1,r2} 后，
   r0 在 `sp`（最低地址），r2 在 `sp+8`。
2. **写回规则**（GBATEK 的 ULD 说明）：基址寄存器也在列表里时——
   - LDM：Rn 是列表最低编号 → 写回**被装载的值**（跳过写回）；
   - STM：Rn 是列表最低编号 → 写回新基址；否则保留旧值。
   直觉：`PUSH {sp}` 这种编码是病态用法，硬件的规则保证栈指针不被
   待存数据覆盖。
3. **LDM 装载 PC（R15 在列表）就是函数返回**：`LDMIA sp!, {r4, pc}`
   一条指令同时恢复寄存器并跳转；带 S 位时（异常模式）还从 SPSR
   恢复 CPSR——这就是中断处理程序的完整出口。

### 2.2 SWP 与"位 6-5"陷阱

`SWP`（原子交换）与半字传输共享"位 7、4 = 1"的编码区。区分依据是
**位 6-5 的两位**：

| 位 6-5 | 指令族 |
|--------|--------|
| 00 | SWP/SWPB（位 22 是 B 字节标志，**不能**拿来判别类型） |
| 01 | LDRH/STRH |
| 10 | LDRSB |
| 11 | LDRSH |

调试实录：我先只判位 5——结果 **LDRSB**（位 6-5 = 10，位 5 = 0）被
误判成 SWP，内存被悄悄改写，导致后面的 LDRSH 读到错误数据；改成只判
位 6，又把 **LDRH**（01）误判了。**两位必须一起判**。这类"部分匹配
编码位"的 bug 不报错、只悄悄污染状态，是模拟器最难查的一类问题。

### 2.3 Thumb：GBA 游戏的主力指令集

Thumb 是 16 位定长指令集。在 16 位宽的 ROM 总线上，一条 ARM 指令要
两次取指，Thumb 只要一次——所以游戏代码几乎全是 Thumb。代价是：

- 大部分指令只能摸到 r0–r7（"低寄存器"），r8–r15 要用专门的格式 5；
- 没有条件执行（只有条件分支）；
- 没有桶形移位器自由组合（移位是独立指令）。

**状态切换**：`BX rN` 按目标地址位 0 切换——位 0 = 1 进 Thumb。所以
Thumb 函数指针总是奇数（`0x08000101`），`POP {pc}` 装载返回地址时
同样按位 0 切状态并抹掉低位。ARMv4 没有 BLX 指令，进 Thumb 只能靠
BX / 异常返回；我们顺带实现了 ARMv5 的 BLX（MBR 骨架里用不到，但
成本几乎为零）。

### 2.4 BL：两条 16 位指令拼一条 32 位跳转

Thumb 的 `BL` 占两条指令位：

```text
第一条（0xF000|hi）：LR = PC可见 + (hi << 12)   ← 暂存高 11 位偏移
第二条（0xF800|lo）：目标 = LR + (lo << 1)
                     LR  = 第二条地址 + 2 | 1   ← 真正的返回地址
```

实现上用 `thumb_pending_bl` 标志把两条"缝"起来：`thumb_step` 看到标志
置位就把当前指令交给 `thumb_bl_complete` 处理。这是 Thumb 里唯一的
跨指令状态，也是单步调试时的经典坑（单步停在这两条之间会看到 LR
里是"半成品偏移"）。

### 2.5 手工汇编：读懂 Thumb 集成测试

集成测试的 Thumb 程序从 0x08000010 起布置（前 16 字节是 ARM 引导段）：

```text
0xF80E = BL 后半        lo = 0x00E → 偏移 = 14×2 = 28（0x1C）
                        目标 = LR(0x08000014) + 0x1C = 0x08000030 = sum5
0xB501 = PUSH {r0, lr}  位 8 置位表示额外存 LR；列表位 0 = r0
0x1808 = ADD r0, r1, r0 位 15-11=00011(F2)？不：0101100…，
                        实际 0x1808 高 6 位 = 000110 → F2 寄存器加法
0xD1FC = BNE -8         cond=NE(0001)，偏移 0xFC 补码 -4 → -4×2 = -8
0x4901 = LDR r1,[pc,#4] 可见 PC = (0x0800003C+4)&~2 = 0x08000040
                        读 0x08000044 的常数池 → 0x02000000
0xBD01 = POP {r0, pc}   弹出两个：r0 恢复现场，pc 弹出返回地址
                        ——返回地址位 0 = 1，硬件自动切回 Thumb
```

调试这个测试时踩的最后一个坑：**常数池的半字顺序**。要存 32 位的
`0x02000000`，u16 数组必须写 `[0x0000, 0x0200]`（低半字在前）——我写成
`[0x0200, 0x0000]`，读出来变成 0x00000200，STR 把结果存去了 0x00000200
（未映射区域，静默丢弃）。字节序问题在 00 篇讲过 BMP、这篇轮到指令流，
**它永远值得多看一眼**。

## 3. 代码走读

### 3.1 Thumb 分派表：本步最大的坑

第一版分派按"GBATEK 格式 1–19"的**编号**当位 15–11 的取值区间——完全
错误：格式编号是文档讲解顺序，不是编码值。`MOV r0,#5`（0x2005）的
`>>11` = 4，被当成了格式 4（ALU），结果寄存器纹丝不动。

修正方法：**用真实指令算出 `>>10` 的值，反推每个格式的位模式区间**
（脚本验算 + mGBA 的 `opcode >> 6` 建表法交叉验证），得到现在的表：

```text
hi = insn >> 10:
  0..=1 F1 移位 | 2..=7 F2 加减 | 8..=15 F3 立即数 | 16 F4 ALU
  17 F5 高寄存器/BX | 18..=19 F6 | 20..=23 F7/F8 | 24..=27 F9
  32..=35 F10 | 36..=39 F11 | 40..=43 F12 | 44 F13 | 45..=47 F14
  48..=51 F15 | 52..=54 F16 | 55 F17 SWI | 56..=59 F18 | 60..=63 F19
```

注意 28..=31（0x7000 区）是保留区，落进去直接忽略。教训写进了
`thumb_execute` 的文档注释：**文档编号 ≠ 编码模式，永远用真实指令
反推分派表**。

### 3.2 块传输的统一算法

`block_transfer` 用一张模式表算出"最低地址 low"，然后无论方向，
寄存器都按编号升序从 low 向上排。写回值由 `new_base` 与 ULD 规则
合成。这个结构让四种模式共享一条循环，也把"寄存器永远小号在低地址"
这条不变式写在了唯一的地方。

### 3.3 Thumb 与 ARM 的 PC 约定统一

Thumb 沿用 01 篇的约定，只是流水线级数不同：

```text
ARM：regs[15] = 指令地址 + 8，取指 = regs[15] - 8，步进 +4
Thumb：regs[15] = 指令地址 + 4，取指 = regs[15] - 4，步进 +2
```

两个状态的"读 PC 可见值"都直接是 `regs[15]`，分支/BL/异常返回各自
维护 `+8` 或 `+4`。F6 的 PC 相对装载还要 `& !2`（Thumb 的 PC 位 1
在字访问时被硬件丢弃）——又一个只在真机资料里找得到的细节。
